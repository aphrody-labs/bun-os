# NTCORE: an NT personality for the Bun OS kernel layer

Status 2026-10-29. Bun OS is a WASM OS (not a boot target). Owner vision: Wine and ReactOS fused at the heart of the
kernel layer, i.e. an NT/Win32 personality next to the Linux 7.3 ABI personality. This document records what the
ReactOS and Wine sources allow, what was built and measured, and the chosen architecture. Everything below was
measured from source on the dates and revisions given; items marked UNVERIFIED were not run.

Not legal advice (see "Licensing").

## 1. What exists

| Piece | Path | State |
|---|---|---|
| Wasm module built from ReactOS C | `packages/ntcore/wasm/ntcore.wasm` (36.7 KB, imports: none) | built, 19 tests pass |
| Build and measurement script | `factory/ntcore/build.ts` (`--sweep` for the compile table) | works on Windows with LLVM 23.1.4 |
| TypeScript API | `packages/ntcore/src/index.ts` | `NtCore`, `Hive`, `HandleTable`, PE inspection |
| Test-side producers | `packages/ntcore/src/hivewriter.ts` (regf writer), PE builder in the test | independent of the C code |
| Sweep results | `factory/ntcore/sweep.json` | per-file pass/fail with first error |
| ReactOS mount | `vendor/reactos` (gitlink e46f4bb1a1ea, `aphrody-labs/reactos`, `update = none`) | registered |

The wasm module links, unchanged, real ReactOS code: `sdk/lib/cmlib` (13 files: the kernel Configuration Manager hive
engine, the same library used by ntoskrnl, freeldr and mkhive), `ntoskrnl/ex/handle.c` (the 3-level Executive handle
table behind every NT handle), `sdk/lib/rtl/image.c` (PE helpers). About 300 lines of glue (`factory/ntcore/glue`)
provide the kernel services these files import: pool allocation, no-op push locks (one wasm thread), a fake PCR and
current thread (`KIP0PCRADDRESS` patched from 0xFFDFF000 to 0x400 in the generated `wdm.h`), a freestanding libc
subset (no wasi-sdk), and a simplified Unicode upcase (Latin-1, Greek, Cyrillic only: UNVERIFIED against the full NLS
table for other scripts, the real `RtlUpcaseUnicodeChar` needs NLS tables).

Measured on this workstation (Windows 11, clang 23.1.4 x86_64-pc-windows-msvc driver, `wasm-ld`, Bun 1.4.4 canary):
headers 237 ms, compile of 19 objects in parallel 673 ms, link 48 ms. Tests: 19 pass in 0.25 s.

Verified by tests: a hive written by the TS writer is accepted by `HvInitialize` and by the kernel's own
`CmCheckRegistry(VALIDATE_HIVE)` (returns 0); case-insensitive path walk with non-ASCII names; 2000-key hive;
inline, out-of-line, DWORD/QWORD/MULTI_SZ values; corrupted signature/checksum/truncation rejected with the cmlib
NTSTATUS; handle table: first handle 4, multiples of 4, 5000 live handles across table levels, reuse after close,
independent tables; PE32 and PE32+ header inspection, RVA to file offset through the section table, data directories,
garbage rejected by `RtlpImageNtHeaderEx`.

Not verified: real-world hives (SYSTEM/SOFTWARE from a Windows install; no such file was used), big-value (`db`) cells
(cmlib itself says "Big keys not supported" for >1 MiB values), hive write path (callbacks return FALSE: read-only),
wasm execution under browsers (only Bun/JSC run).

(`tools/make_requests`) that was not run (UNVERIFIED).

## 3. Source facts (top 15, paths relative to the checkouts under `C:\Users\aphro\src\ref\`)

1. `reactos/sdk/lib/cmlib` (10.3 kLOC) is built for three hosts (NT kernel, bootloader, host tools via `CMLIB_HOST`):
   it is designed to be OS-independent, which is why it ports with a 200-line glue.
2. `reactos/ntoskrnl/ex/handle.c` (1502 lines) is the NT handle table; its only external needs are pool, push locks,
   APC bookkeeping and quota (13 symbols), all stubbed.
3. ReactOS builds headers with a host tool: `reactos/sdk/tools/hpp` expands `sdk/include/xdk/*.template.h` into
   `ntdef.h`, `wdm.h`, `ntddk.h`, `ntifs.h`, `winnt.h`. It is a 631-line C file, built here with a host compiler.
4. ReactOS NT 5.2 x86 ABI is ILP32; wasm32 is ILP32, so `HANDLE_TABLE_ENTRY`, `CM_KEY_NODE` etc. keep their i386
   layouts. x86_64 NT (LLP64) layouts do not map to wasm32; PE32+ images are only inspected, never run.
5. `reactos/ntoskrnl/sysfuncs.lst` lists 296 Nt/Zw system service entries; Wine's `dlls/ntdll/ntdll.spec` declares 248
   `-syscall` entries (231 `Nt*`). These are the two candidate tables for the kernel ABI; they overlap but are not
   identical (Wine adds Unix-only helpers, ReactOS has per-version drift).
6. `reactos/ntoskrnl` is about 220 kLOC across ob/ps/io/mm/ex/se/config (counts: ob 12.8k, ps 16.2k, io 43.4k,
   mm 51.6k, ex 23.0k, se 21.0k, config 18.8k lines).
7. `reactos/win32ss` is 696 files, 373 kLOC (win32k: user, gdi, csrss). It depends on the hardware-oriented GDI
   engine and on user32 message semantics; no cheap piece was identified.
8. `reactos/hal` is 30.8 kLOC of mostly x86 platform code (PIC, APIC, CMOS, DMA); for wasm the HAL is a thin custom
   layer (timer, interrupt = JS event, no devices), not a port.
9. Wine's server (`wine-cachyos/server`, 56 kLOC) is the userspace NT kernel: objects, handles (`handle.c`), registry
   (`registry.c`), processes, threads, sockets, windows. Its transport is Unix sockets and `SCM_RIGHTS` fd passing
   (`request.c`, `fd.c`), which have no wasm equivalent; the protocol itself is a generated table (`protocol.def`).
10. Wine's ntdll syscalls run on the PE side (`dlls/ntdll`, 176 kLOC incl. `unix/`) and call a Unix side
    (`dlls/ntdll/unix`, 59 kLOC) through a syscall dispatcher with inline asm per CPU (`signal_i386.c` etc.).
11. Wine 9.0 `server/` has `esync.c` and `fsync.c` (futex-based); there is NO `ntsync` source in the local checkout:
    the local `wine-cachyos` tree is Wine 9.0 at f80ddae while the Proton line in `proton-cachyos` is 11.0-20261015.
    The CachyOS ntsync/fsync delta is therefore not present in the tree measured here (UNVERIFIED for the synced fork).
12. Wine's PE-side code needs x86 inline asm in two public headers (`include/winnt.h` NtCurrentTeb and RtlFailFast,
    `include/wine/asm.h` function emitters); both patched in copies, not in the fork.
13. `wine-cachyos/dlls/win32u` (90 kLOC), `winewayland.drv` (6.6 kLOC), `winevulkan` (7 kLOC) are the win32k-less
    path: win32u implements user/gdi on top of driver entry points; `winewayland.drv` shows the compositor-protocol
    driver shape that Bun OS would implement over its own window protocol.
14. Existing browser/wasm work (search 2026-10-29): Boxedwine (32-bit x86 emulator compiled to wasm running a wasm
    build of Wine, ~12 MB first boot), "Wine Assembly" (x86 interpreter in WAT running Win98-era PE files), and
    the v86 PC emulator (x86 to wasm JIT) which lists ReactOS as working. No project compiles ReactOS ntoskrnl or
    Wine's server to wasm natively. Nothing was installed or run.
15. wasm cannot execute native x86 PE code. Any x86 `.exe` needs an x86 emulator (v86, Boxedwine-style, Bochs) as
    the CPU; only PE files rebuilt for wasm (mingw-w64/llvm-mingw has no wasm32 target in the local toolchain
    `llvm-mingw-20261020`, which targets i686/x86_64/armv7/aarch64 only) can use the NT personality as a native runtime.

## 4. Architecture options and decision

| Option | What it is | Evidence | Cost | Fusion depth | Verdict |
|---|---|---|---|---|---|
| (a) Rust/wasm Nt* personality over Bun OS services + PE loader | Own implementation of the Nt* ABI, handle/registry/object semantics taken from ReactOS and Wine as specification and as reusable libraries | cmlib + ex/handle + rtl/image run in wasm today (36.7 KB) | low to medium, incremental | ABI-level fusion: ReactOS data structures and algorithms, Wine's userspace-kernel structure | PRIMARY |
| (b) Compile ReactOS ntoskrnl components (ob, ps, cm, io) to wasm32 with a thin HAL | Use the real kernel code, replace Ke/Hal/Mm | 112 / 112 files of ob+ps+se+config+io compile; 66 / 70 of ex+mm | high: Ke (dispatcher, APC, DPC, scheduler) and Mm are the hard part; wasm has no preemption, no page tables | deepest | STRETCH, component by component: `cm` done, `ex` handle table done, `ob` next |
| (c) Compile Wine ntdll / server subset to wasm32-wasi and bridge syscalls | Reuse the Unix-style userspace NT | 20 / 36 PE-side ntdll files compile; server blocked on protocol generator and Unix IPC | high: `ntdll/unix` is the Linux bridge (futex, mmap, sockets) which the Linux personality could provide | medium | LATER: valuable once the Linux 7.3 personality exists (Wine runs on top of it) |
| (d) ReactOS or Wine as guest in a wasm x86 emulator | v86/Bochs + ReactOS ISO or Wine userland | v86 lists ReactOS as working (not run here) | lowest | none | FALLBACK for unmodified x86 binaries; not the kernel |

Decision. Primary: (a), built so that every kernel structure comes from ReactOS code where it compiles and runs in
wasm (b, applied selectively) and the process model and wire protocol are modeled on Wine's server. Stretch: (b)
for `ob` (object directory, handle creation through `ObpCreateHandle`), then `ps`/`io` against a Bun OS HAL.
(c) is deferred until the Linux personality exists. (d) is the only route for native x86 PE binaries and is the
`wasmos` agent's area; ntcore only needs to expose its syscall table to it. Order of next work:
1. Nt* syscall table skeleton generated from `ntoskrnl/sysfuncs.lst` with argument counts, dispatching to JS or wasm.
2. `ob`: link `ntoskrnl/ob` (11 files compile) on top of the handle table; objects for File, Key, Event, Section.
3. Wire `NtOpenKey/NtQueryValueKey` to `Hive` for a mounted default SYSTEM/SOFTWARE hive (writer needed: cmlib's
   write path with file callbacks).
4. PE32/PE32+ section mapping and import resolution (loader), producing the process image for wasm-recompiled
   programs; x86 binaries go to the emulator.
5. Console and GUI via the compositor protocol, modeled on `winewayland.drv`.

## 5. Caveats found while measuring

- The local `wine-cachyos` reference is Wine 9.0 (f80ddae); origin/os pins `vendor/wine-cachyos` to the same commit.
  The agent syncing the forks could not be reached by message (not reachable at the time); ntsync content is
  UNVERIFIED for the synced fork.
- The build environment needs a host C compiler only for `hpp`. On this machine plain `clang` has no libc headers,
  so `llvm-mingw` (`x86_64-w64-mingw32-clang`) built it.
- wasi-sdk was not downloaded: the module is freestanding (`wasm32-unknown-unknown`), which keeps it import-free
  and kernel-like. Whether wasi-sdk's newest 2026 release changes anything is UNVERIFIED. `buncc` has a wasm
  provider for Rust (`packages/buncc/src/providers/wasm.ts`); no `buncc c` wasm C target was exercised.
- Hive limitations: cmlib read path only; `HvSyncHive` write needs working file callbacks.

## 6. Licensing (not legal advice)

- ReactOS is GPL-2.0-or-later (some parts LGPL, BSD, MIT, public domain: the xdk headers say "NOT COPYRIGHTED").
  `ntcore.wasm` statically links GPL ReactOS objects, so it is a GPL-2.0-or-later combined work; the package is
  declared `GPL-2.0-or-later` and the ReactOS revision is recorded in `packages/ntcore/wasm/ntcore.build.json`.
  Distributing it requires offering the corresponding source (this repository plus `vendor/reactos`).
- Wine is LGPL-2.1-or-later (Proton and CachyOS patches carry their own notices). Linking Wine objects statically
  into a GPL-2.0+ module is permitted by the LGPL-to-GPL clause, but mixing Wine into an Apache/MIT-licensed core
  would require the LGPL relinking terms.
- Consequence for Bun OS: the NT personality should stay a separable, optionally loaded module (as `ntcore` is) so
  that the MIT/Apache parts (Bun, TS API consumers over the wasm ABI) are not made derivative by default. Whether a
  process boundary (wasm module with an ABI) is enough to avoid derivative-work status is a legal question that was
  not examined. Seek legal advice before shipping a combined image.
- GPL-2.0-only versus -or-later and GPL-3 compatibility of other Bun OS components were not audited.

```
NTCORE_REACTOS=<reactos checkout> NTCORE_WINE=<wine-cachyos checkout> NTCORE_HOST_CC=<cc with libc> \
  bun factory/ntcore/build.ts --sweep
cd packages/ntcore && bun test
```

`submodule:vendor/wine-cachyos`, `npm:@aphrody/buncc` and `npm:@aphrody/windows`. The `wasmos` edge is not recorded
because no such component id exists yet.
