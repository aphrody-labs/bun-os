# NTCORE: an NT personality for the Bun OS kernel layer

Status 2026-10-29. Bun OS is a WASM OS (not a boot target). Owner vision: Wine and ReactOS fused at the heart of the
kernel layer, i.e. an NT/Win32 personality next to the Linux 7.3 ABI personality. This document records what the
ReactOS and Wine sources allow, what was built and measured, and the chosen architecture. Everything below was
measured from source on the dates and revisions given; items marked UNVERIFIED were not run.

Not legal advice (see "Licensing").

## 1. What exists

| Piece | Path | State |
|---|---|---|
| Wasm module built from ReactOS C | `packages/ntcore/wasm/ntcore.wasm` (36.7 KB, imports: none) | built, 19 tests pass |
| Build and measurement script | `factory/ntcore/build.ts` (`--sweep` for the compile table) | works on Windows with LLVM 23.1.4 |
| TypeScript API | `packages/ntcore/src/index.ts` | `NtCore`, `Hive`, `HandleTable`, PE inspection |
| Test-side producers | `packages/ntcore/src/hivewriter.ts` (regf writer), PE builder in the test | independent of the C code |
| Sweep results | `factory/ntcore/sweep.json` | per-file pass/fail with first error |
| ReactOS mount | `vendor/reactos` (gitlink e46f4bb1a1ea, `aphrody-labs/reactos`, `update = none`) | registered |

The wasm module links, unchanged, real ReactOS code: `sdk/lib/cmlib` (13 files: the kernel Configuration Manager hive
engine, the same library used by ntoskrnl, freeldr and mkhive), `ntoskrnl/ex/handle.c` (the 3-level Executive handle
table behind every NT handle), `sdk/lib/rtl/image.c` (PE helpers). About 300 lines of glue (`factory/ntcore/glue`)
provide the kernel services these files import: pool allocation, no-op push locks (one wasm thread), a fake PCR and
current thread (`KIP0PCRADDRESS` patched from 0xFFDFF000 to 0x400 in the generated `wdm.h`), a freestanding libc
subset (no wasi-sdk), and a simplified Unicode upcase (Latin-1, Greek, Cyrillic only: UNVERIFIED against the full NLS
table for other scripts, the real `RtlUpcaseUnicodeChar` needs NLS tables).

Measured on this workstation (Windows 11, clang 23.1.4 x86_64-pc-windows-msvc driver, `wasm-ld`, Bun 1.4.4 canary):
headers 237 ms, compile of 19 objects in parallel 673 ms, link 48 ms. Tests: 19 pass in 0.25 s.

Verified by tests: a hive written by the TS writer is accepted by `HvInitialize` and by the kernel's own
`CmCheckRegistry(VALIDATE_HIVE)` (returns 0); case-insensitive path walk with non-ASCII names; 2000-key hive;
inline, out-of-line, DWORD/QWORD/MULTI_SZ values; corrupted signature/checksum/truncation rejected with the cmlib
NTSTATUS; handle table: first handle 4, multiples of 4, 5000 live handles across table levels, reuse after close,
independent tables; PE32 and PE32+ header inspection, RVA to file offset through the section table, data directories,
garbage rejected by `RtlpImageNtHeaderEx`.

Not verified: real-world hives (SYSTEM/SOFTWARE from a Windows install; no such file was used), big-value (`db`) cells
(cmlib itself says "Big keys not supported" for >1 MiB values), hive write path (callbacks return FALSE: read-only),
wasm execution under browsers (only Bun/JSC run).

## 3. Source facts (top 15, paths relative to the checkouts under `C:\Users\aphro\src\ref\`)

1. `reactos/sdk/lib/cmlib` (10.3 kLOC) is built for three hosts (NT kernel, bootloader, host tools via `CMLIB_HOST`):
   it is designed to be OS-independent, which is why it ports with a 200-line glue.
2. `reactos/ntoskrnl/ex/handle.c` (1502 lines) is the NT handle table; its only external needs are pool, push locks,
   APC bookkeeping and quota (13 symbols), all stubbed.
3. ReactOS builds headers with a host tool: `reactos/sdk/tools/hpp` expands `sdk/include/xdk/*.template.h` into
   `ntdef.h`, `wdm.h`, `ntddk.h`, `ntifs.h`, `winnt.h`. It is a 631-line C file, built here with a host compiler.
4. ReactOS NT 5.2 x86 ABI is ILP32; wasm32 is ILP32, so `HANDLE_TABLE_ENTRY`, `CM_KEY_NODE` etc. keep their i386
   layouts. x86_64 NT (LLP64) layouts do not map to wasm32; PE32+ images are only inspected, never run.
5. `reactos/ntoskrnl/sysfuncs.lst` lists 296 Nt/Zw system service entries; Wine's `dlls/ntdll/ntdll.spec` declares 248
   `-syscall` entries (231 `Nt*`). These are the two candidate tables for the kernel ABI; they overlap but are not
   identical (Wine adds Unix-only helpers, ReactOS has per-version drift).
6. `reactos/ntoskrnl` is about 220 kLOC across ob/ps/io/mm/ex/se/config (counts: ob 12.8k, ps 16.2k, io 43.4k,
   mm 51.6k, ex 23.0k, se 21.0k, config 18.8k lines).
7. `reactos/win32ss` is 696 files, 373 kLOC (win32k: user, gdi, csrss). It depends on the hardware-oriented GDI
   engine and on user32 message semantics; no cheap piece was identified.
8. `reactos/hal` is 30.8 kLOC of mostly x86 platform code (PIC, APIC, CMOS, DMA); for wasm the HAL is a thin custom
   layer (timer, interrupt = JS event, no devices), not a port.
9. Wine's server (`wine-cachyos/server`, 56 kLOC) is the userspace NT kernel: objects, handles (`handle.c`), registry
   (`registry.c`), processes, threads, sockets, windows. Its transport is Unix sockets and `SCM_RIGHTS` fd passing
   (`request.c`, `fd.c`), which have no wasm equivalent; the protocol itself is a generated table (`protocol.def`).
10. Wine's ntdll syscalls run on the PE side (`dlls/ntdll`, 176 kLOC incl. `unix/`) and call a Unix side
    (`dlls/ntdll/unix`, 59 kLOC) through a syscall dispatcher with inline asm per CPU (`signal_i386.c` etc.).
11. Wine 9.0 `server/` has `esync.c` and `fsync.c` (futex-based); there is NO `ntsync` source in the local checkout:
    the local `wine-cachyos` tree is Wine 9.0 at f80ddae while the Proton line in `proton-cachyos` is 11.0-20261015.
    The CachyOS ntsync/fsync delta is therefore not present in the tree measured here (UNVERIFIED for the synced fork).
12. Wine's PE-side code needs x86 inline asm in two public headers (`include/winnt.h` NtCurrentTeb and RtlFailFast,
    `include/wine/asm.h` function emitters); both patched in copies, not in the fork.
13. `wine-cachyos/dlls/win32u` (90 kLOC), `winewayland.drv` (6.6 kLOC), `winevulkan` (7 kLOC) are the win32k-less
    path: win32u implements user/gdi on top of driver entry points; `winewayland.drv` shows the compositor-protocol
    driver shape that Bun OS would implement over its own window protocol.
14. Existing browser/wasm work (search 2026-10-29): Boxedwine (32-bit x86 emulator compiled to wasm running a wasm
    build of Wine, ~12 MB first boot), "Wine Assembly" (x86 interpreter in WAT running Win98-era PE files), and
    the v86 PC emulator (x86 to wasm JIT) which lists ReactOS as working. No project compiles ReactOS ntoskrnl or
    Wine's server to wasm natively. Nothing was installed or run.
15. wasm cannot execute native x86 PE code. Any x86 `.exe` needs an x86 emulator (v86, Boxedwine-style, Bochs) as
    the CPU; only PE files rebuilt for wasm (mingw-w64/llvm-mingw has no wasm32 target in the local toolchain
    `llvm-mingw-20261020`, which targets i686/x86_64/armv7/aarch64 only) can use the NT personality as a native runtime.

## 4. Architecture options and decision

| Option | What it is | Evidence | Cost | Fusion depth | Verdict |
|---|---|---|---|---|---|
| (a) Rust/wasm Nt* personality over Bun OS services + PE loader | Own implementation of the Nt* ABI, handle/registry/object semantics taken from ReactOS and Wine as specification and as reusable libraries | cmlib + ex/handle + rtl/image run in wasm today (36.7 KB) | low to medium, incremental | ABI-level fusion: ReactOS data structures and algorithms, Wine's userspace-kernel structure | PRIMARY |
| (b) Compile ReactOS ntoskrnl components (ob, ps, cm, io) to wasm32 with a thin HAL | Use the real kernel code, replace Ke/Hal/Mm | 112 / 112 files of ob+ps+se+config+io compile; 66 / 70 of ex+mm | high: Ke (dispatcher, APC, DPC, scheduler) and Mm are the hard part; wasm has no preemption, no page tables | deepest | STRETCH, component by component: `cm` done, `ex` handle table done, `ob` next |
| (c) Compile Wine ntdll / server subset to wasm32-wasi and bridge syscalls | Reuse the Unix-style userspace NT | 20 / 36 PE-side ntdll files compile; server blocked on protocol generator and Unix IPC | high: `ntdll/unix` is the Linux bridge (futex, mmap, sockets) which the Linux personality could provide | medium | LATER: valuable once the Linux 7.3 personality exists (Wine runs on top of it) |
| (d) ReactOS or Wine as guest in a wasm x86 emulator | v86/Bochs + ReactOS ISO or Wine userland | v86 lists ReactOS as working (not run here) | lowest | none | FALLBACK for unmodified x86 binaries; not the kernel |

Decision. Primary: (a), built so that every kernel structure comes from ReactOS code where it compiles and runs in
wasm (b, applied selectively) and the process model and wire protocol are modeled on Wine's server. Stretch: (b)
for `ob` (object directory, handle creation through `ObpCreateHandle`), then `ps`/`io` against a Bun OS HAL.
(c) is deferred until the Linux personality exists. (d) is the only route for native x86 PE binaries and is the
`wasmos` agent's area; ntcore only needs to expose its syscall table to it. Order of next work:
1. Nt* syscall table skeleton generated from `ntoskrnl/sysfuncs.lst` with argument counts, dispatching to JS or wasm.
2. `ob`: link `ntoskrnl/ob` (11 files compile) on top of the handle table; objects for File, Key, Event, Section.
3. Wire `NtOpenKey/NtQueryValueKey` to `Hive` for a mounted default SYSTEM/SOFTWARE hive (writer needed: cmlib's
   write path with file callbacks).
4. PE32/PE32+ section mapping and import resolution (loader), producing the process image for wasm-recompiled
   programs; x86 binaries go to the emulator.
5. Console and GUI via the compositor protocol, modeled on `winewayland.drv`.

## 5. Caveats found while measuring

- The local `wine-cachyos` reference is Wine 9.0 (f80ddae); origin/os pins `vendor/wine-cachyos` to the same commit.
  The agent syncing the forks could not be reached by message (not reachable at the time); ntsync content is
  UNVERIFIED for the synced fork.
- The build environment needs a host C compiler only for `hpp`. On this machine plain `clang` has no libc headers,
  so `llvm-mingw` (`x86_64-w64-mingw32-clang`) built it.
- wasi-sdk was not downloaded: the module is freestanding (`wasm32-unknown-unknown`), which keeps it import-free
  and kernel-like. Whether wasi-sdk's newest 2026 release changes anything is UNVERIFIED. `buncc` has a wasm
  provider for Rust (`packages/buncc/src/providers/wasm.ts`); no `buncc c` wasm C target was exercised.
- Hive limitations: cmlib read path only; `HvSyncHive` write needs working file callbacks.

## 8. bunos.sys: the Bun OS Windows kernel driver (2026-11-03)

The native half of the NT personality: a WDM driver in Rust (`windows-drivers-rs`: `wdk` 0.5, `wdk-sys` 0.5.2,
`wdk-build` 0.6) that runs inside the Windows 11 kernel, with no sandbox between it and the Bun OS userland.

| Piece | Path | State |
|---|---|---|
| Contract | `crates/bunos-nt-proto` (`no_std`, dependency-free) | control codes + fixed little-endian layouts + strict, fuzz-tested parsers, shared verbatim by the driver and every client so the two sides cannot drift |
| Driver | `crates/bunos-nt-driver` (package `bunos`, own workspace, `panic = "abort"`, static CRT) | builds with WDK/SDK 10.0.28000; depends on `bunos-nt-proto` |
| INF source | `crates/bunos-nt-driver/bunos.inx` | primitive driver (`[DefaultInstall.NTamd64]`, no hardware ID), service `BunOS`, demand start, Driver Store (DirId 13) |
| Package | `cargo wdk build --profile release` (cargo-wdk 0.2.0) | `bunos.sys`, `bunos.inf` (stampinf), `bunos.cat` (inf2cat), infverif passes, `.sys` and `.cat` test-signed |
| Rust client | `crates/bunos-nt-client` (windows-rs 0.62.2, own workspace) | `Device::open/version/ping/caps/configure/read_events`, CLI `bunos-nt status/version/caps/ping/events`; exit 3 absent, 4 not elevated |
| bun:ffi client | `packages/windows/src/nt-driver.ts` (`@aphrody/windows/nt-driver`, `ntDriver`) | `BunOsDevice.open()` (null when absent, throws on access denied), `version/ping/caps/configure/readEvents`, strict `decodeCaps/decodeEvents`, `available()` |
| Test VM | `factory/wsl/windows/vm/` (`vm.sh`, `autounattend.xml`, `setup.cmd`, `test-driver.cmd`) | Windows 11 LTSC eval under QEMU/KVM on the build host |

**Scope — user mode first, no vulnerable-driver primitives.** WinClean (section 9) is the control plane of the whole
PC through Win32/WinRT/NT APIs; the kernel driver adds only what user mode cannot do. Deliberately absent, and they
stay absent: no arbitrary kernel or physical-memory read/write, no I/O-port or MSR access, no code-execution IOCTL.
Those are exactly what turns a signed driver into an exploitable "vulnerable driver" (BYOVD) used to disable security
software; every control code returns kernel-produced data, never memory the caller chooses, and kernel image/object
addresses are never exposed (KASLR stays intact). Each new kernel service is a new, versioned control code whose
input is parsed by `bunos-nt-proto` (exact length, ABI number, reserved fields and every enumerated value checked)
before the driver acts, with fuzz-style tests on the parsing side.

Contract — ABI 1, `CTL_CODE(FILE_DEVICE_UNKNOWN, fn, METHOD_BUFFERED, access)`. Device `\Device\BunOS`, link
`\\.\BunOS`, DACL `D:P(A;;GA;;;SY)(A;;GA;;;BA)` applied by `IoCreateDeviceSecure` so only SYSTEM and Administrators
can open it:

| IOCTL | Code | Access | In → out |
|---|---|---|---|
| `VERSION` | `0x00222000` | any | — → `"bunos.sys <ver>\0"` |
| `PING` | `0x00222004` | any | bytes → same bytes |
| `CAPS` | `0x00226008` | read | — → `Caps` (ABI, sources supported/active, ring capacity, counters) |
| `EVENTS_CONFIG` | `0x0022E040` | read+write | `{abi,sources mask}` → `Caps`; enables exactly the given sources (0 disables all) |
| `EVENTS_READ` | `0x00226044` | read | — → header + up to N 256-byte `Record`s drained from the kernel ring |

Event sources are kernel notification callbacks, monitor only (they never block or alter the operation): `process`
(`PsSetCreateProcessNotifyRoutineEx`, create with image path + exit), `thread` (`PsSetCreateThreadNotifyRoutine`),
`image` (`PsSetLoadImageNotifyRoutine`; user images carry base+size, kernel images none), `registry`
(`CmRegisterCallbackEx`, set/delete value and delete key). Events go into a 512-slot non-paged ring behind one spin
lock, drop-newest on overflow with a counter; closing the last handle disables every source. All three clients pin
the codes and layouts in tests; the registry altitude is `385210.4207`.

Release package measured on the workstation (`%CARGO_TARGET_DIR%\release\bunos_package`):

`bunos.sys` imports only `ntoskrnl.exe` (the process/thread/image/registry callback routines, the spin lock and the
precise clock) and `wdmsec.lib` statically (`WdmlibIoCreateDeviceSecure`). The release package is measured in the
build bundle's `SHA256SUMS`; hashes change with every rebuild (the signature carries a timestamp and stampinf a
DriverVer), so they are not pinned here.

Signing: the `aphrody-labs/bun` test certificate is machine-wide `CN=Bun OS Test Signing, O=Aphrody`
(`factory/windows/signing/test-signing.ps1`, LocalMachine `My`/`Root`/`TrustedPublisher`). `cargo wdk build`
test-signs with its local `WDRLocalTestCert`; the install/bundle step re-signs `bunos.sys`/`bunos.cat` and the
`.exe`s with the machine certificate so they are trusted here. User-mode binaries so signed load with Secure Boot on;
the **kernel driver loads only in test-signing mode, which Secure Boot forbids** — loading it is an owner step
(section 9).

## 9. WinClean NT tools, the WSL bridge and owner-run driver loading (2026-11-03)

User mode is the control plane; the driver only feeds it kernel events. The surfaces:

| Piece | Path | What |
|---|---|---|
| WinClean `nt_*` tools | `packages/bun-windows-winclean/src/nt.rs` | `nt_status`, `nt_events_start/read/stop`, `nt_handles`, `nt_kernel_modules`; in the 193-tool catalog, reached from the aphrody MCP and `aphrody` CLI like every other WinClean tool |
| WSL bridge | `crates/bunos-nt-bridge` (`bunos-winbridge`) | serves the WinClean catalog to the Bun OS WSL guest over hvsocket; `serve`, `service`, `tools` |
| Guest client | `crates/bunos-nt-bridge/client/bunos-win.ts` | the `bunos win <tool> [jsonArgs]` client the WSL agent wires into the guest |
| Install | `factory/windows/nt/{setup-elevated.ps1,build-nt-bundle.ts}` | `%SystemRoot%\BunOS` system install + `BunOSWinBridge` service |
| Driver load / test | `factory/windows/nt/driver/{load-driver,test-driver}.cmd`, `factory/windows/nt/end-to-end.ts` | owner-run load + the end-to-end check |

**`nt_*` tools.** Every one works whether or not `bunos.sys` is loaded. `nt_status` reports the driver state
(`loaded` / `access-denied` when not elevated / `absent`), ABI and caps. `nt_events_start` opens a kernel session
(process/thread/image/registry sources) when the driver is loaded and the process is elevated, otherwise it falls
back to a user-mode process-create/exit poll; `nt_events_read` drains it. `nt_handles` and `nt_kernel_modules` are
pure user-mode `NtQuerySystemInformation` calls (handle table with object-type names; loaded kernel images) with the
object pointers and image bases stripped. The buffer parsers are bounds-checked and fuzz-tested.

**Bridge.** Windows is exposed to the Linux side (WSL) over hvsocket: `AF_HYPERV` on the Windows host, `AF_VSOCK` in
the guest, newline-delimited JSON, one request per line `{token,id,tool,args}`. A shared token
(`%SystemRoot%\BunOS\bridge.token`, SYSTEM+Administrators ACL, shared read-only into the guest) gates every
connection; a wrong token drops it. An **allow-list** (`DEFAULT_ALLOW`) serves only read-only / diagnostic tools —
including the `nt_*` event streams — and an **absolute deny-list** (`DENY`) blocks anything that changes the machine
(`tweak_apply`, `delete_*`, `set_registry_value`, `kill_process`, `mem_write_*`, `nt_events_start/stop`) even if an
operator adds an `--allow` prefix; a guest that needs those uses the elevated WinClean path directly. The serve loop
is transport-agnostic: `--transport loopback` (TCP on 127.0.0.1) is used to test on the workstation before any WSL
distro exists, `--transport hvsocket` is the real guest transport. The WSL bundle is owned by the other agent
(`factory/wsl/`, `docs/WSL.md`); coordinate through this interface only, and test against the distro once `wsl -l -v`
shows it.

```
# workstation, no driver, no elevation: the whole chain over loopback
cargo build --release -p bunos-nt-client -p bunos-nt-bridge
bun factory/windows/nt/end-to-end.ts            # ffi contract + loopback bridge (hello, nt_status, allow-list, token)
```

**System install (elevated, idempotent).** Everything lands in `%SystemRoot%\BunOS`, like `cmd.exe` or
`explorer.exe`, with a sha256-checked manifest, no overwrites and an uninstall path — the same layout the WSL and
userland agents use:

```
bun  factory/windows/nt/build-nt-bundle.ts                                        # -> %LOCALAPPDATA%\BunOS\bundle\bunos-nt
C:\Windows\System32\sudo.exe pwsh -NoProfile -File factory\windows\nt\setup-elevated.ps1 -Bundle <bundle>
#   bin\{bunos-nt.exe,bunos-winbridge.exe} (signed) + System32 hard links where the name collides with nothing,
#   nt\bunos-win.ts, nt\driver\{bunos.sys,bunos.inf,bunos.cat,load-driver.cmd,test-driver.cmd}, bridge.token,
#   manifests\nt.json, and the BunOSWinBridge service (demand start).  -Plan previews, -Uninstall reverses it,
#   -StartBridge starts the service.  sc start BunOSWinBridge  runs it.
```

The driver package is staged under `nt\driver\` but **never loaded by the install** and never copied by hand into
`System32\drivers`: that is `pnputil`'s job at owner-run load time, through the INF.

**Owner-run driver loading (documented, not performed by any agent).** The driver changes the kernel's trust
boundary, so loading it is a manual owner decision with its security trade-offs stated here:

- *Test signing (development).* Our certificate is self-signed. Windows loads a kernel driver signed by it only in
  test-signing mode, and test-signing mode requires **Secure Boot OFF** (with Secure Boot on, `bcdedit /set
  testsigning on` is refused — "protected by Secure Boot policy"). Steps the owner performs: disable Secure Boot in
  firmware; elevated `bcdedit /set testsigning on`; reboot; then
  `C:\Windows\System32\sudo.exe cmd /c %SystemRoot%\BunOS\nt\driver\load-driver.cmd`
  (`pnputil /add-driver bunos.inf /install`, `sc start BunOS`) and `test-driver.cmd`
  (`bunos-nt version/caps/ping/events`). Trade-off: test-signing mode and Secure Boot off weaken the machine's boot
  trust for every driver, not only ours, and a "Test Mode" watermark appears. Reverse with `sc stop BunOS`,
  `pnputil /delete-driver bunos.inf /uninstall`, `bcdedit /set testsigning off`, re-enable Secure Boot.
- *Attestation signing (production).* To load with Secure Boot on and no test mode, submit `bunos.sys` to the
  Microsoft Partner Center hardware dashboard for **attestation signing** (an EV code-signing certificate and a
  Partner Center account are required); Microsoft returns a cab signed so the driver loads on normal machines. This
  is the only way to ship the driver to an owner who keeps Secure Boot on. Trade-off: it ties the driver to our
  Partner Center identity and Microsoft's attestation policy, and each revision is re-submitted.

Until the owner loads it, `bunos.sys` is **not** loaded on the workstation, and no agent enables test signing or
changes boot configuration here. Everything above (`nt_*` user-mode paths, the bridge, both clients) runs and is
tested without it; the kernel paths are verified in the Windows 11 VM (section 8) and by the owner post-reboot.
