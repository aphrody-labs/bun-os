# Bun OS should adopt uutils side by side

uutils is now a family of roughly 13 Rust reimplementations of the GNU base system, and only **coreutils is production-grade**. Coreutils passes about **93-95% of the GNU test suite** (653 pass, 21 fail at release 0.12.0) and is Ubuntu's default since 25.10. The siblings (findutils, diffutils, sed, shadow) are advanced but unproven, and grep, tar, procps, awk, util-linux and bsdutils are early or partial. No distro other than Ubuntu defaults to any of it. For Bun OS, an Arch/pacman distribution that tracks external projects as pinned owners, the evidence supports a conservative path. Ship Arch's prefix-only `uutils-coreutils` next to GNU `coreutils`, add findutils and diffutils the same way, and expose bare names only through a dedicated PATH directory. Keep GNU `cp`, `mv`, `rm`, `install` and `stty` until upstream closes its race-condition bugs. Do not replace the `coreutils` package: the one AUR attempt at that broke `mkinitcpio` and was removed. uutils has no shell, and the only bash-compatible Rust shell found, brush, is not recommended for production, so bash stays. Nothing here was tested on an Arch host, and several figures come from secondary sources, flagged below.

## One flagship tool and a fast-growing, uneven family

The org holds 31 repositories, none of them forks, and nearly all were pushed within the last week of October 2026. Coreutils has about 24.3k stars; the next tier is findutils (653), diffutils (280), util-linux (226), grep (136), procps (117) and sed (110) ([org listing](https://github.com/orgs/uutils/repositories?q=sort%3Astars)). The star gap shows that attention and real-world testing are concentrated on one project. The org's strategy is now clearly "the whole base system": per-package repos exist for findutils (find, xargs, locate, updatedb), diffutils (diff, cmp, diff3, sdiff), sed, grep, awk, tar, procps, util-linux, shadow, acl, hostname and bsdutils, plus shared libraries such as `uucore`, `parse_datetime`, `platform-info` and `num-prime`.

Maturity falls into rough tiers. These are my judgment, since no README claims production readiness. Findutils and diffutils both state a drop-in-replacement goal ([findutils](https://github.com/uutils/findutils), [diffutils](https://github.com/uutils/diffutils)). Sed claims all POSIX features, three complex test scripts running correctly and faster speed than GNU and FreeBSD sed in most benchmarks, with GNU regex compatibility still planned ([sed](https://github.com/uutils/sed)). Shadow lists **28 implemented tools** (passwd, useradd, usermod, chage, newuidmap and others), claims bit-for-bit GNU output for passwd and pwck, and is tested in a Docker matrix across Debian, Alpine and Fedora. Its static musl build has no PAM, NSS or yescrypt, and `su` lives in sudo-rs instead ([shadow](https://github.com/uutils/shadow)). Lower down, grep calls itself "an initial release and may contain bugs" and ignores `LANG`, treating non-UTF-8 matches as binary ([grep](https://github.com/uutils/grep)). Awk is a work in progress that treats GNU differences as bugs and runs against gawk's own suite ([awk](https://github.com/uutils/awk)). Procps lists 18 "ongoing" tools and is Linux-only ([procps](https://github.com/uutils/procps)). Util-linux marks only **14 of about 60 tools as started** ([util-linux](https://github.com/uutils/util-linux)), and bsdutils has only `renice` started ([bsdutils](https://github.com/uutils/bsdutils)). Tar (97 open issues) is built on the `tar-rs` library ([tar](https://github.com/uutils/tar)). The `red` sed experiment and the `login` and `uutils-args` repos are retired, with `login` folded into `shadow`.

The assembled picture is a near-complete GNU base set plus sudo-rs, with real gaps. Most of util-linux (mount, fdisk, lsblk, losetup) is missing. So are logger, script and wall from bsdutils, and compression tools such as gzip. I found no `patch` implementation, though diffutils speaks of patch compatibility. These gap items are my analysis, not source claims. Exact GNU pass rates for the non-coreutils tools exist only as chart images in the `*-tracking` repos and were not captured. Release pages also scraped empty, so current versions of the siblings must be checked on crates.io.

## Coreutils is 93-95% compatible, with concentrated risk in file-mutating tools

The latest release seen is **0.12.0 (2026-09-17)**: 653 pass, 21 fail, 0 error, plus Ubuntu-compatibility fixes, a pure-Rust `fancy-regex` replacing the C `onig` dependency in `expr`, and Windows builds of `nice`, `nohup` and `hostid` ([releases API](https://api.github.com/repos/uutils/coreutils/releases?per_page=12)). Main already reads 0.13.0 ([Cargo.toml](https://raw.githubusercontent.com/uutils/coreutils/main/Cargo.toml)). Release 0.11.0 (2026-08-31) added PGO builds claimed "up to 31% faster" for some utilities, relative to earlier uutils builds rather than to GNU. Reported pass rates climbed from 88% at 0.5.0 to 90.58% at 0.9 and **93.48% (645 of 690) at 0.10** ([Linuxiac](https://linuxiac.com/rust-based-uutils-coreutils-0-10-reaches-93-5-gnu-compatibility/)). The denominators differ (about 675 versus 690 tests) and the trend is not monotonic. A uutils/awk pull request shows the GNU reference moving from 9.10 to 9.11 added 25 tests and lowered the percentage with no regression ([awk PR 33](https://github.com/uutils/awk/pull/33)). I could not reconcile the 0.10, 0.11 and 0.12 release dates, so treat the cadence as roughly monthly pre-1.0 releases. The project's stated position is that differences from GNU are bugs ([README](https://github.com/uutils/coreutils)). The remaining 7% still matters: scripts that depend on edge behaviour will break. I found **no credible uutils-versus-GNU benchmark**. The only one surfaced was a single blogger's report of `sha256sum` running about 2.3x slower, which is a secondary source ([computingforgeeks](https://computingforgeeks.com/ubuntu-2604-rust-coreutils-guide/)). Bun OS should run its own.

Security findings show the shape of the risk. A Canonical-funded Zellic audit across two rounds (December 2025 to March 2026) found **113 issues and 44 CVEs** (CVE-2026-35338 through CVE-2026-35381), mostly logic and time-of-check/time-of-use (TOCTOU) races rather than memory errors, and most are reported resolved. The audit explicitly excluded build pipelines and distro packaging ([Ubuntu Discourse](https://discourse.ubuntu.com/t/an-update-on-rust-coreutils/80773)). That scoping leaves supply-chain review of roughly 500 vendored crates (a commenter's figure, unconfirmed by Canonical) to whoever packages it.

Build and licensing facts matter for a Cargo-centric workspace. The MSRV is **Rust 1.88.0** on edition 2024, and nightly is not required ([Cargo.toml](https://raw.githubusercontent.com/uutils/coreutils/main/Cargo.toml)). It builds as one multicall binary or as per-utility binaries, with `make install` options `PREFIX`, `DESTDIR`, `PROG_PREFIX=uu-`, `MULTICALL=y`, `COMPLETIONS` and `MANPAGES`; `cargo install` yields no completions or man pages ([README](https://github.com/uutils/coreutils)). The tools are also separate `uu_*` crates on crates.io (for example `uu_ls` 0.12.0), but I found no API-stability statement, so pin `uucore` and all `uu_*` crates in lockstep. The license is MIT with a strict clean-room contributor policy that bars reading GPL/LGPL implementations and rejects GPL dependencies ([CONTRIBUTING](https://raw.githubusercontent.com/uutils/coreutils/main/CONTRIBUTING.md)). That policy keeps the MIT licensing coherent for a distribution that must preserve license notices. One known Arch hazard is that uutils `install` breaks `mkinitcpio` ([AUR notes](https://aur.archlinux.org/pkgbase/coreutils-uutils)).

## Only Ubuntu defaults to uutils, and it carved out cp, mv and rm

Ubuntu 25.10 was the first major distro to default to uutils coreutils and sudo-rs, using 25.10 as a rehearsal for the 26.04 LTS ([sudo-rs plan](https://discourse.ubuntu.com/t/adopting-sudo-rs-by-default-in-ubuntu-25-10/60583)). The 25.10 rollout hit a real incident. A `date -r` bug made a timestamp difference always zero, so `unattended-upgrades` silently never ran until the fix landed in rust-coreutils 0.2.2-0ubuntu2 ([OMG Ubuntu](https://www.omgubuntu.co.uk/2025/10/ubuntu-25-10-rust-coreutils-date-bug), [Phoronix](https://www.phoronix.com/news/Ubuntu-25.10-Broken-Upgrade)). Ubuntu 26.04 LTS ships **0.8.0 with GNU `cp`, `mv` and `rm` held back** because of 8 open TOCTOU issues as of 2026-04-22, targeting "100% rust-coreutils" in 26.10 ([Canonical](https://discourse.ubuntu.com/t/an-update-on-rust-coreutils/80773)). A report dated 2026-09-15 says those three moved to uutils for 26.10, after a July 2026 attempt that broke live-image builds was reverted ([It's FOSS](https://itsfoss.com/news/ubuntu-rustification-coreutils-migration/)). The mechanism is a provider metapackage: essential `coreutils` depends on `coreutils-from-uutils` (default) or `coreutils-from-gnu`, and `build-essential` hard-depends on the uutils provider. Ubuntu also archives `rust-diffutils` 0.4.2, but whether findutils or diffutils are defaults I could not establish ([packages.ubuntu.com](https://packages.ubuntu.com/stonking/rust-diffutils)). Reported side effects include `install` replacing a destination symlink such as `/sbin`, AppArmor profiles that name `/usr/bin/ls` literally, and `uname -p` printing `unknown`. The last two come from a secondary guide. The pattern is that filesystem-mutating tools and path- or symlink-sensitive consumers regress first.

Everywhere else uutils is opt-in. Debian packages `rust-coreutils` under `/usr/lib/cargo/bin/coreutils`, with a README advising against production use (from 0.6.0, possibly dated) ([Debian README](https://sources.debian.org/src/rust-coreutils/0.6.0-1/debian/README.Debian)). Fedora approved 0.5 for F44 with no plan to make it default ([FESCo](https://fedoraproject.org/wiki/Changes/Rust_Uutils_Coreutils_0.5_Nushell_0.109)). NixOS offers `uutils-coreutils-noprefix` as an opt-in, and Alpine carries it in community. Chimera Linux uses FreeBSD-derived chimerautils instead ([chimerautils](https://git.omada.cafe/chimera-linux/chimerautils/src/tag/v14.1.1)). Arch has **`extra/uutils-coreutils` 0.12.0-1** (MIT; depends on glibc, libgcc, openssl, systemd-libs; 15.7 MB), where every binary under `/usr/bin` carries a `uu-` prefix, so it coexists with core `coreutils` ([Arch package](https://archlinux.org/packages/extra/x86_64/uutils-coreutils/), [file list](https://archlinux.org/packages/extra/x86_64/uutils-coreutils/files/)). The AUR holds `uutils-findutils` 0.9.1-2 (its maintainer is open to moving it to extra once binary naming is settled) and `uutils-diffutils-bin` ([AUR](https://aur.archlinux.org/packages/uutils-findutils/)). The conflicting AUR drop-in `coreutils-uutils` still built GNU `install`, `stty`, `chcon` and `runcon`, broke `mkinitcpio`, and appears to have been removed in early 2026 ([Arch forum](https://bbs.archlinux.org/viewtopic.php?id=311729)). Official `sudo-rs` is in extra (0.2.12-0.2.13 per package pages), and Debian-family alternatives such as `update-alternatives` do not exist on Arch ([Arch sudo-rs](https://archlinux.org/packages/extra/x86_64/sudo-rs)).

## A side-by-side integration plan fits Bun OS's pinned-owner model

The recommended design follows the lowest-risk precedent on each side: Arch's prefix-only packaging and Ubuntu's decision to hold back the racy tools. These are my recommendations, not sourced facts. First, register coreutils, findutils, diffutils, sed and shadow as pinned external owners, tracking upstream tags (0.12.x for coreutils) and recording the GNU-suite pass rate per pin. Their MIT licenses and clean-room policy fit the repository's rule to preserve imported notices, and MSRV 1.88 sits comfortably under the workspace's nightly toolchain. These crates belong to nested upstream workspaces, so consuming them as pinned external projects, rather than migrating them into the root Cargo workspace, matches the current state of the migration. Build on the VPS under the serialized wrapper. Second, in the Arch repo, depend on `uutils-coreutils` from extra and build `uutils-findutils` and `uutils-diffutils` into the Bun OS repository with consistent `uu-` naming. None of these conflicts with `coreutils`, which `base` depends on. Third, instead of a symlink farm in `/usr/bin` (which collides with `coreutils` file ownership, and which the AUR treated as a policy problem), ship a small package such as `bunos-uutils-links` that places bare-name symlinks in a dedicated directory such as `/usr/lib/bunos/uutils/bin`. Put that directory on PATH only for chosen shells, services or the Rust-centric dev images. Fourth, if a full swap is ever wanted, use a `provides=coreutils` / `conflicts=coreutils` package with pacman hooks, but keep GNU `cp`, `mv`, `rm`, `install`, `stty`, `chcon` and `runcon`, and gate it on a clean `mkinitcpio`, `makepkg` and pacman-hook run.

The shell question has a short answer. The uutils org has no shell. The web search found one bash-compatible Rust shell, **brush** (MIT, v0.4.0), which tests itself against real bash by comparing stdout and exit codes across 850 to 1700 tests depending on the source ([brush](https://github.com/reubeno/brush)). It does not support `select`, handles `set -e` only partially, and is not recommended for production. `thewtex/shell` is an early alpha, and `bashrs` is a Rust-to-POSIX-shell transpiler, not a shell. Bun OS should keep GNU bash as `/bin/sh` and login shell and treat brush as an opt-in experiment, so that no uutils component ends up interpreting `PKGBUILD`s, hooks or init scripts.

## Conclusion

The central finding is that "uutils" is really two projects. Coreutils is a 24k-star, audited, Ubuntu-default tool with a known, narrow residual risk, while the rest of the org is a fast-moving pipeline of drop-in goals with unpublished or unread compatibility numbers. A Rust-centric distribution gains most from the first and should pin the others as experiments, promoting each only when its GNU-suite tracking repo and a Bun OS smoke run agree. The Ubuntu experience shows the failures that matter are operational, not memory-safety bugs: a silent `date` regression, symlink handling in `install`, and path-sensitive confinement profiles.

Open questions before committing include how current the Debian and Fedora versions are, whether Ubuntu defaults findutils or diffutils, and the official Arch package's exact multicall layout. All GNU test pass rates other than coreutils are unknown, and the 8-to-0 TOCTOU closure for `cp`, `mv` and `rm` should be re-verified against 0.13 before Bun OS considers moving those tools. The first concrete step is to qualify `uutils-coreutils` 0.12.x on the VPS: build the initramfs, run `makepkg`, run the pacman hooks, and benchmark against GNU.
