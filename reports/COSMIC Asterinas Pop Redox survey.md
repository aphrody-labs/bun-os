# Bun OS should consume COSMIC, track Redox, pilot Asterinas

Only one of the four projects is ready to ship in Bun OS today. COSMIC Epoch is a stable, Rust-native desktop that Arch already packages, so the COSMIC Desktop composition can install it with pacman and needs no source import. The other three belong in the pinned-owner model for different reasons. Asterinas is a Rust framekernel that targets Linux ABI compatibility, and it is the most credible kernel-level pilot but pins an exact nightly that Bun OS must carry. Redox OS is a separate microkernel OS with its own Podman-based build and patched toolchain, so it is a tracked external owner and a source of crates, not a distribution base. pop-os/pop is a management repo and not an OS source tree, so it serves as an index and licensing map. Licensing is manageable throughout (GPL-3.0 and MPL-2.0 for COSMIC and Asterinas, MIT for Redox's build repos), but each project has different toolchain demands. COSMIC needs a recent stable Rust (1.93 to 1.95), Asterinas needs one pinned nightly, and Redox needs its own patched compilers. Bun OS's single nightly contract therefore cannot be assumed to cover all of them. Several facts remain unverified and are flagged below.

## COSMIC Epoch is stable, modular and already in Arch

cosmic-epoch is a pure aggregation repo, not a workspace: **31 git submodules** (compositor, panel, applets, settings, greeter, session, portal, files, terminal, store and others) plus a root `justfile` that builds and installs them all ([.gitmodules](https://raw.githubusercontent.com/pop-os/cosmic-epoch/master/.gitmodules), [justfile](https://raw.githubusercontent.com/pop-os/cosmic-epoch/master/justfile)). There is no single Cargo workspace. Each component builds through its own justfile or Makefile, and the README tells distros to package per component with no backwards-compatibility guarantees ([README](https://github.com/pop-os/cosmic-epoch)). Epoch 1 shipped stable with Pop!_OS 24.04 LTS in December 2025 ([The Register](https://www.theregister.com/2025/12/22/popos_2404_cosmic_epoch_1/)). By October 2026 the release page shows **1.11.0 (20 October)**, with minor releases every one to three weeks since August ([releases](https://github.com/pop-os/cosmic-epoch/releases)). The tag scheme is `epoch-X.Y.Z`, and the README says tags exist mainly for non-Pop distros, because Pop!_OS updates submodules before tagging.

Architecturally the stack is all Rust. The toolkit is libcosmic (MPL-2.0, built on a pinned iced fork), the compositor cosmic-comp sits on Smithay with Xwayland enabled, and cosmic-protocols is MIT ([libcosmic](https://github.com/pop-os/libcosmic), [cosmic-comp](https://raw.githubusercontent.com/pop-os/cosmic-comp/master/Cargo.toml), [cosmic-protocols](https://raw.githubusercontent.com/pop-os/cosmic-protocols/main/Cargo.toml)). The two binaries whose manifests were checked, cosmic-session and cosmic-comp, are **GPL-3.0-only, edition 2024**, with rust-version 1.93 and 1.95 respectively ([cosmic-session](https://raw.githubusercontent.com/pop-os/cosmic-session/master/Cargo.toml)). The licence is therefore mixed, and per-repo LICENSE files must be checked for the other submodules, since icons, wallpapers and the sound theme were not verified. No nightly requirement appeared in the manifests checked, so COSMIC builds need a stable Rust at least 1.95, not Bun OS's repo nightly. Unless the nightly in use is new enough to satisfy 1.95, the VPS needs a second toolchain for this composition.

The integration path is short because Arch ships COSMIC in `extra` as a `cosmic` package group. The direct fetch listed 29 entries at **1.10.0-1**, one release behind upstream, and pointed to `cosmic-session` as the entry package ([Arch group](https://archlinux.org/groups/x86_64/cosmic/)). A search snippet showed 1.0.16 on the same page, which conflicts, so run `pacman -Si` before pinning. Arch renames some packages (cosmic-terminal for cosmic-term, cosmic-text-editor for cosmic-edit, cosmic-workspaces for cosmic-workspaces-epoch). Login needs `cosmic-greeter.service` enabled ([README](https://raw.githubusercontent.com/pop-os/cosmic-epoch/master/README.md)). I recommend that the COSMIC Desktop composition be a package list resolved through libalpm from Arch and CachyOS repositories. It stays separate from the Server and Gamescope compositions, with its own session entry. Vendoring cosmic-epoch as a pinned owner only makes sense if Bun OS needs patches or builds ahead of Arch. In that case track `epoch-X.Y.Z` tags, build per component with `prefix=/usr` and `rootdir=$pkgdir`, and expect to build on the VPS with a stable toolchain. The PKGBUILD sources and the ArchWiki page were not read, so dependency lists remain unconfirmed.

## pop-os/pop indexes Pop!_OS but contains no OS to build

pop-os/pop describes itself as "A project for managing all Pop!_OS sources". It holds helper scripts, `REPOS.md`, `LICENSING.md` and the central issue tracker, about 1.8k open issues at fetch time, and no distribution code ([pop-os/pop](https://github.com/pop-os/pop)). Pop!_OS itself is Ubuntu-based, uses apt and per-repo `debian/` folders, and gets COSMIC through its own build system. REPOS.md maps the real components: distinst (installer backend), system76-power, system76-firmware, firmware-manager, the launcher, and forks of the Ubuntu kernel and linux-firmware ([REPOS.md](https://github.com/pop-os/pop/blob/master/REPOS.md)). The org licence policy is explicit: **GPL-3.0-only for applications, MPL-2.0 for libraries that must link with other licences, and MIT OR Apache-2.0 for foundational libraries**, with an SPDX identifier in each file ([LICENSING.md](https://github.com/pop-os/pop/blob/master/LICENSING.md)).

For Bun OS this makes pop-os/pop a reference to track, not a dependency. COSMIC is decoupled from Pop: Pop!_OS is one distribution channel among Arch, Fedora, NixOS, openSUSE and Gentoo ([cosmic-epoch README](https://github.com/pop-os/cosmic-epoch)). The reusable parts are few. pop-launcher is the most portable (MPL-2.0, Rust, JSON over stdin and stdout, used by cosmic-launcher) ([launcher](https://github.com/pop-os/launcher)). distinst is LGPL-3.0 and assumes a squashfs image and apt, so a pacman installer would need a new libalpm backend ([distinst](https://github.com/pop-os/distinst)). system76-power is GPL-3.0 and mainly matters on hybrid-graphics laptops ([system76-power](https://github.com/pop-os/system76-power)). pop-upgrade, the ISO tooling and the Ubuntu-derived kernel are apt-specific and not worth lifting. Bun OS could pin pop-os/pop for REPOS.md and LICENSING.md drift only. Pop!_OS 26.04 status and Epoch 2 scope are unconfirmed, so do not plan against either.

## Asterinas offers a safe-Rust kernel with a strict nightly pin

Asterinas is a Linux-ABI-compatible kernel built as a "framekernel": a small privileged unsafe core (OSTD) plus every other kernel service in safe Rust inside one address space. The USENIX ATC 2025 paper puts the memory-safety TCB at about **14.0%** of the codebase and claims performance on par with Linux, though the abstract gives no figures ([USENIX ATC25](https://www.usenix.org/conference/atc25/presentation/peng-yuke)). The OSTD book describes the core `ostd` crate as roughly 10K lines, and I could not reconcile that with the 14% ratio ([OSTD book](https://asterinas.github.io/book/ostd/index.html)). The codebase is over 250,000 lines, about 200,000 of them Rust ([0.19.0 announcement](https://asterinas.github.io/2026/10/13/announcing-asterinas-0.19.0.html)). Release 0.19.0 (13 October 2026) added hypervisor support in OSTD, a DRM stack, X.Org on a software-GL path and a first self-hosted build, where Nix, Cargo, rustc and QEMU run on Asterinas.

Maturity is promising but pre-production. The README claims **240+ syscalls**, with x86-64 as Tier 1 and TDX, ARM64 and RISC-V as Tier 2 ([GitHub](https://github.com/asterinas/asterinas)). Release 0.18.0 verified over 100 packages on Asterinas NixOS, including Firefox and QEMU ([0.18.0](https://asterinas.github.io/2026/06/04/announcing-asterinas-0.18.0.html)). Kernel modules will never load, and SysV IPC, io_* AIO, splice and fanotify are unsupported, though the compatibility page may be stale ([Linux compatibility](https://asterinas.github.io/book/kernel/linux-compatibility/)). Phoronix calls DRM and AArch64 "initial" and makes no production claim ([Phoronix](https://www.phoronix.com/news/Asterinas-0.19-Released)). I read this as a viable kernel for virtualised guests (Firecracker, Cloud Hypervisor, QEMU) and not yet a desktop bare-metal kernel, since drivers are virtio-centric and Linux driver reuse is impossible by design.

The build contract matters most for Bun OS. `rust-toolchain.toml` pins **nightly-2026-07-21** with rust-src, rustc-dev and llvm-tools-preview ([rust-toolchain.toml](https://raw.githubusercontent.com/asterinas/asterinas/main/rust-toolchain.toml)). Builds expect a Docker dev container or a Nix flake, using `make kernel` and `make run_kernel`. `ostd` and `cargo-osdk` are on crates.io under **MPL-2.0**, with 0.19.0 published on 2026-10-12 ([crates.io](https://crates.io/api/v1/crates/ostd)). MPL-2.0 is file-level copyleft, so it can link with other code, and modified MPL files must stay MPL. The licence is mainly MPL-2.0 with more permissive terms on some components ([GitHub](https://github.com/asterinas/asterinas)). Bun OS already runs a nightly Rust toolchain, so Asterinas fits better than any other project here, but the pin must match exactly or the OSDK template drifts. I found no semver policy for `ostd`, and minors arrive every four to six months, so pin by commit or tag. The best candidates are a pinned external owner under Bun OS Infra, a VM-guest kernel image built on the VPS, and an optional `ostd` dependency for new safe-Rust components.

## Redox OS is a separate OS whose pieces Bun OS can mine

The `redox` repo is the build-system entry point of a Rust microkernel OS: it lists the kernel, base (system components and drivers), RedoxFS, relibc, Ion, Orbital, pkgutils and Redoxer as components, built through Podman and `make` ([redox README](https://gitlab.redox-os.org/redox-os/redox/-/raw/master/README.md)). The repo is MIT-licensed and the old `cookbook` is archived, with recipes merged in ([cookbook](https://gitlab.redox-os.org/redox-os/cookbook)). Each recipe is a `recipe.toml` under `recipes/`, and `make repo-lock` pins recipe commits ([build reference](https://doc.redox-os.org/book/build-system-reference.html)). That makes Redox a natural pinned-owner candidate, though the notes found no submodule list, so Bun OS would pin the `redox` repo and its component repos by commit.

Maturity is the weakest of the four. The last numbered release is **0.9.0 (2024-09-09)**, and no newer release appeared by October 2026 ([0.9.0](https://redox-os.org/news/release-0.9.0)). Progress ships as monthly reports and daily server and desktop images, so pins must track commits and not tags. September 2026 brought DRM-style graphics drivers, Intel Tiger Lake hotplug and new relibc calls. Packages exist for x86-64, ARM64, RISC-V and i586, but page-fault handling is x86-64 and i586 only ([Sep 2026](https://www.redox-os.org/news/this-month-260930/)). COSMIC Files, Editor, Terminal and Reader run on Redox, and cosmic-comp ran only as a winit proof of concept in February 2026 ([Feb 2026](https://www.redox-os.org/news/this-month-260228/)). Redox's own ABI policy makes only libredox stable, and relibc and `redox_syscall` stay unstable ([Libraries and APIs](https://doc.redox-os.org/book/libraries-apis.html)).

The toolchain is the real obstacle. `make prefix` and `make all` download a patched rustc, GCC and LLVM from Redox servers, and the Book does not state a nightly channel ([build reference](https://doc.redox-os.org/book/build-system-reference.html)). The kernel moved to Rust edition 2024 ([Sep 2025](https://www.redox-os.org/news/this-month-250930/)). Podman and Linux orientation mean builds belong on the VPS, serialised under the shared factory slots, never on the Windows workstation. Kernel and drivers rely on the scheme model and are not drop-in for Linux, so the realistic reuse is crate-level: relibc, RedoxFS and pkgar-style packaging, all MIT by assumption. Per-component licences for relibc, kernel, RedoxFS and Orbital were not verified, and recipe ports keep upstream licences, so track those per recipe.

## Comparison and recommended tracking model

| Project | Role for Bun OS | Toolchain | Licence | Maturity signal |
|---|---|---|---|---|
| COSMIC Epoch | Consume from Arch `extra` (1.10.0 seen; upstream 1.11.0); optional pinned owner | Stable Rust 1.93 to 1.95, edition 2024, `just` | GPL-3.0-only apps, MPL-2.0 libcosmic, MIT protocols | Stable since Dec 2025, releases every 1 to 3 weeks |
| pop-os/pop | Reference index only | Python 3 plus launchpadlib for scripts | GPL-3.0 default, MPL-2.0 libs | Meta repo, about 1.8k open issues |
| Asterinas | Pinned external owner, VM-guest kernel pilot | nightly-2026-07-21 exactly, Docker or Nix, QEMU | Mainly MPL-2.0 | 0.19.0, 240+ syscalls, pre-production |
| Redox OS | Pinned external owner, crate mining | Redox-patched rustc, GCC, LLVM via Podman | MIT (redox, cookbook verified) | Release 0.9.0 (2024), daily images |

The pattern for the pinned owners follows AGENTS.md: register Asterinas and Redox as external pinned owners and keep upstream histories and licences intact. Do not migrate them into the root Cargo workspace, because both ship their own workspaces and toolchain files, and nested boundaries are the stated reason for the current exclusions. Give each its own toolchain lane on the VPS within the four-compiler-job-per-lane limit. That means the stable lane for COSMIC rebuilds, the exact-nightly lane for Asterinas and the Podman lane for Redox.

## Conclusion

The sharpest finding is that "Rust-centric" does not mean "one toolchain". Four Rust projects need three incompatible compiler contracts, and Bun OS's single nightly is the right fit only for Asterinas. Workspace unification is therefore a packaging and ownership question and not a Cargo one, which supports the owners' existing stance of not claiming a single Cargo workspace.

Sequence matters. COSMIC delivers value immediately through pacman and should land first. Asterinas is the best investment for a kernel story, starting as a Firecracker or QEMU guest build and watching for 0.20 and the DRM and AArch64 maturity signals. Redox stays a watch-and-mine owner until it issues a release after 0.9.0 and shows desktop-grade hardware support. Verify these open items before committing pins: the Arch `cosmic` group version conflict, per-component COSMIC and Redox licences, Redox's exact toolchain pin, and `ostd`'s API stability policy.
